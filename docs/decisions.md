# Decisions

One line per decision, with its reason and the date it was made.
Decisions marked "kick-off" come from the planning conversation before the first session.

| Date | Decision | Reason |
|---|---|---|
| kick-off | The Vita reader shows a comic panel by panel. | A full page is unreadable on a 960x544 screen. |
| kick-off | Two parts: a PC tool finds the panels and writes a Vita-ready CBZ with `panels.json`; a Vita app steps through the panels. | Reason not recorded in the brief. |
| kick-off | This phase answers only one question: which panel detector is good enough. | Everything else depends on the detector; whether a correction step is needed is decided from the results. |
| kick-off | The test comic is a black-and-white manga, read right to left. | Reason not recorded in the brief. |
| kick-off | The PC side is Python only, one program. | Both detectors are Python; no second language to maintain. |
| kick-off | Python rules: type hints on every function, checked with `pyright`; dataclasses for structured data; small modules with one job each. | Reason not recorded in the brief. |
| kick-off | `uv` manages Python and dependencies; `uv.lock` is committed. | The environment must be the same on macOS and on Linux. |
| kick-off | Compare Kumiko (classical, OpenCV contours) with Magi (model trained on manga). | One classical and one learned approach. |
| kick-off | Fallback detectors (three YOLO models on Hugging Face) are tried only if Magi is unusable or poor. | Keep the comparison small. |
| kick-off | Every detector's result is converted to one shared panel JSON format. | Detectors and UIs stay interchangeable. |
| kick-off | Comparison UI is FiftyOne, one label field per detector. | Open source (Apache 2.0) and has detection evaluation built in. |
| kick-off | The Vita app will be written in C with vitasdk. | Reason not recorded in the brief. |
| kick-off | Quality target: under 1% of panels wrong (bad rectangle, missed panel, false panel, wrong order). | Above that the comic becomes unpleasant to read. |
| kick-off | No correction tooling is built in advance. | Whether it is needed is decided from this phase's results. |
| kick-off | Comic pages and archives are never committed. | They are copyrighted. |
| 2026-10-09 | Python 3.12. | Inside the supported range of every library considered (FiftyOne: 3.10 to 3.13). |
| 2026-10-09 | The Python package and project are called `komawari`. | Owner's choice; it is the manga term for dividing a page into panels. |
| 2026-10-09 | The Python project sits at the repository root with a `src/` layout; the Vita code will go in `vita/`. | Nothing has to move when the Vita app starts. |
| 2026-10-09 | Source comic archives go in `comics/`, selected test pages in `pages/`; both are git-ignored. | Keeps the full comic apart from the small test set. |
| 2026-10-09 | `pyproject.toml` has no author name or email. | Owner's choice. |
| 2026-10-09 | Git ignores comic archives and all image files anywhere in the repository. | Safety net against committing a copyrighted page by accident. |
| 2026-10-09 | Licence concerns (Kumiko is AGPL, Magi is non-commercial) are recorded in `licences.md` but not acted on yet. | First see and confirm what works. |
| 2026-10-09 | First look uses 10 random pages (`komawari sample`, seed 1) instead of hand-picked hard pages. | Owner's choice: see and confirm what works first. Hard pages come after. |
| 2026-10-09 | The first comparison view is a local HTML report (`results/report.html`), not FiftyOne. | Owner's request: see panels and reading direction next to the original page. FiftyOne stays open for later. |
| 2026-10-09 | Kumiko is a git submodule in `third_party/kumiko` and runs as a separate command, once per page. | It is not an installable package; the submodule fixes the exact commit on every machine. |
| 2026-10-09 | Magi v3 is fixed to revision `49c73a2` and `transformers` to 4.45.2. | Its downloaded code fails on transformers 5.x, and a fixed revision means that code cannot change unnoticed. |
| 2026-10-09 | Magi's panel order is kept as the model returns it. | Shows what the detector really gives; whether to re-sort is still open. |
| 2026-10-09 | Comic archives are read with the `bsdtar` command. | The test comic is a CBR (RAR), which Python cannot open itself; bsdtar reads CBZ and CBR alike. |
| 2026-10-09 | Shared panel format, first draft: per page `file`, `width`, `height` and `panels` as `x`, `y`, `width`, `height` in pixels, listed in reading order. | The least that the detectors and the report need. Not yet reviewed together. |
| 2026-10-09 | The report uses reduced copies of the pages (1600 pixels wide). | Full pages are 4130 x 5960 and make a browser slow. |
| 2026-10-09 | `results/` is git-ignored. | It is generated, and the reduced page copies in it are copyrighted. |
| 2026-10-09 | Chosen pages are added by printed page number (`komawari add`); the number is read from the end of the file name. | In this archive the two match: checked by eye on 20 pages. Spread files such as `018-019` count for both numbers. |
| 2026-10-09 | The test set is the 10 random pages plus 12 pages chosen by the owner for being hard. | The random pages were all ordinary; the chosen ones have slanted borders and art that crosses borders. |
| 2026-10-09 | Kumiko is the panel detector. | Owner's choice after the comparison: open licence, adjustable, keeps sound effects that cross borders. Its errors are accepted for now. |
| 2026-10-09 | `panels.json` format 1, described in `docs/panels-format.md`: pages in reading order, each with its size and its panels as `x`, `y`, `width`, `height`. | The same shape the detector runners already use, plus a version number, title and reading direction. |
| 2026-10-09 | Each `panels.json` gives rectangles in the pixels of the images next to it. `komawari resize` writes a second, converted file for the smaller Vita images. | The reader needs no scaling code, and resizing does not need a new detection run. |
| 2026-10-09 | A page gets an empty panel list, which means "show the whole page", when its file name has no page number, when only one panel was found, or when the panels cover less than half of it. | Kumiko marks boxes on covers, extras, title and text pages, and the reader cut them oddly; 27 of the 409 pages of the first volume prepared. A single panel leaves nothing to step through. |
| 2026-10-09 | Pages keep the archive's own order. | The cover comes first there; sorted by name it would come last. |
| 2026-10-09 | Prepared comics go in `books/<name>/` (git-ignored). | Extracted pages are copyrighted and large. |
| 2026-10-09 | Vita pages fit within 4096 x 2560 pixels; a normal page becomes 1774 x 2560. | 4096 is the Vita's texture limit. At 2560 high, 83% of the test volume's panels have at least the screen's resolution when fitted to 960 x 544 (62% at 2048, 95% at 3072), for an 18 MB texture. To be confirmed on the device. |
| 2026-10-09 | Vita pages are JPEG, quality 90; greyscale pages stay greyscale. | Decodes several times faster than PNG on the Vita's slow processor, and the files are smaller. |
| 2026-10-09 | The reader is written in C with SDL2 and is developed first on the desktop in a 960 x 544 window. | The same code runs on macOS, Linux and the Vita, so each step can be tried in seconds. Owner agreed. |
| 2026-10-09 | The Vita SDK goes in `~/vitasdk`, not the documented `/usr/local/vitasdk`. | `/usr/local` needs administrator rights; the SDK works from any folder that `VITASDK` points to. |
| 2026-10-09 | The reader's code lives in `reader/`; `CMakeLists.txt` and `CMakePresets.json` sit at the repository root, with presets `desktop` and `vita`. | An IDE reads the presets from the project root. This replaces the earlier plan of a `vita/` folder, because the code also runs on the desktop. |
| 2026-10-09 | The reader's first version is the bare minimum that runs on an emulator. | Owner's choice. |
| 2026-10-09 | JSON is read with cJSON 1.7.19, a git submodule in `third_party/cJSON`. | Small, MIT licence, plain C; the Vita SDK has no C JSON library. |
| 2026-10-09 | Comics are kept one folder per comic. On the Vita the reader lists the folders in `ux0:data/komawari`; on the desktop those in the folder given as its argument, or else in `for_vita/`. | Owner's request. With the desktop default, running it from an IDE needs no settings. |
| 2026-10-09 | Controls: see the table in `README.md`. The reading direction is not used yet. | To be revisited once it is used on a device. |
| 2026-10-09 | The Vita build has a CMake target `emulator` that builds the package and starts it in Vita3K. | One step from an IDE or the terminal. |
| 2026-10-09 | The Vita build finds the SDK through `VITASDK`, or else in `~/vitasdk`. | An IDE that is not started from a terminal may not see variables set in the shell profile. |
| 2026-10-09 | Reader display: the picture glides from panel to panel; the rest of the page stays visible but dimmed; a new page fades in; a progress bar and one square per panel appear for 1.5 seconds after each step; Up arrow, D-pad up or Triangle switches between the panel and the whole page. | Owner asked for a nicer UI. No text is drawn, so no font is needed yet. The dimmed surroundings also show art that Kumiko's rectangle cut off. |
| 2026-10-09 | The `emulator` target copies `for_vita/` to Vita3K's memory card before starting it (macOS path only). | The emulator kept an old `panels.json` after the comic was prepared again. |
| 2026-10-09 | `komawari prepare` does everything for one comic and writes its Vita-ready folder to `for_vita/NAME/`; the full-size pages stay in `books/NAME/`. | One command per comic, and one folder whose contents go to the Vita. |
| 2026-10-09 | Each Vita-ready comic has a `cover.jpg`, 544 pixels high, from its first upright page. | The reader shows covers where a comic is chosen; loading full pages for that would not fit in the Vita's memory. |
| 2026-10-09 | The reader starts on a shelf: the comics' covers in a row, the chosen one in the middle. No titles are drawn. | Needed once there is more than one comic; still no font. |
| 2026-10-09 | The reader's code is split into one file per job (`main`, `library`, `shelf`, `reading`, `book`, `shot`, `motion`, `draw`, `input`) and formatted with `clang-format`. | Owner asked for code that is nice to read. |
| 2026-10-10 | With a single comic the reader skips the shelf and opens it. On the shelf, START opens a comic as well as Cross, and a small picture of the Cross button sits under the chosen cover. | With one comic the shelf looked like a broken reader: the arrow keys did nothing, and nothing showed what to press. |
| 2026-10-10 | When Kumiko fails on a page, the page gets no panels (shown whole) and the run goes on; failures are listed at the end. | Kumiko crashed on one page of a volume and stopped the whole comic. |
| 2026-10-10 | The reader has its own artwork, drawn by `komawari artwork`: a logo mark of three panels with slanted gutters, the name in Dela Gothic One, and three colours (ink, paper and one accent). | Owner asked for a professional look on a real Vita. Drawn by code so that a new name or colour is one constant and a rerun, and so that no comic art is used. |
| 2026-10-10 | The page behind the bubble is laid out as a comic page of three panels with slanted gutters: the name top left, the tagline bottom left, and a tall accent-coloured panel on the right, drawn around the place where the Vita puts its start button (layout style `psmobile`). | The page shows what the reader does. The Vita fixes the start button's place, so the panel was shaped around it after the owner asked for the button to sit in the middle of its panel. |
| 2026-10-10 | The app is called Komawari. | It is the manga term for dividing a page into panels, it is already the project's name, and it is short. Confirmed by the owner. |
| 2026-10-10 | `.gitignore` lets the PNG files in `reader/sce_sys/` through. | They are the reader's own artwork, not comic pages. |
| 2026-10-10 | The logo mark and the lettering are approved by the owner. The accent colour is azure, `#3D8FE6`, instead of vermilion. | Owner's choice among four blues. |
| 2026-10-10 | The page behind the bubble is dark: ink panels, paper lettering, one azure panel. The paper-coloured version and its `--dark` switch were removed. | Owner's choice, and it matches the dark reader that follows. The artwork is final. |
| 2026-10-10 | `komawari prepare` without arguments prepares every archive in `comics/` and skips, with a line of output, each comic whose folder in `for_vita/` already exists. Each stage is skipped when its result exists, so the separate `resize` command is gone. | Owner's request. Deleting `for_vita/NAME` redoes only the resizing; deleting `books/NAME` as well redoes everything. |
| 2026-10-10 | `komawari test` checks 5 random numbered pages of the comic that arrived in `comics/` last and writes `test/report.html`. "Arrived last" is read from the file's changed time. | Owner's request. A copied file keeps its original created and modified dates, so only the changed time tells when it was copied in. |
| 2026-10-10 | `komawari transfer` and `komawari list` work on a Vita connected over USB in VitaShell's USB mode: the memory card appears as a drive, recognised by its `app` and `appmeta` folders. | Owner's request for both commands. USB because a comic is about 650 MB; no network address is needed. Wi-Fi (FTP) is not supported. |
| 2026-10-10 | `transfer` copies `panels.json` last and skips files already on the card with the right size. | The reader only lists a folder that holds `panels.json`, so it never shows half a comic, and an interrupted copy can be run again. |
| 2026-10-10 | `komawari prepare --ltr` prepares a comic that reads left to right; without it, right to left. The direction goes to Kumiko and into `panels.json`. | Western comics. One flag for the comics prepared in that run; already prepared comics are skipped anyway. |
| 2026-10-10 | `komawari prepare --force` prepares a comic again from scratch. | Instead of deleting folders by hand. |
| 2026-10-10 | `prepare` deletes a comic's extracted full-size pages once its Vita copy exists, also for comics it skips. `books/NAME/panels.json` stays. | The pages take about 1.3 GB per comic and can be extracted from the archive again in seconds. |
| 2026-10-10 | `komawari transfer` also updates a comic that was prepared again: it compares the two `panels.json` files, and always writes that file. | A changed `panels.json` can have exactly the size of the old one, so comparing sizes is not enough. |
| 2026-10-10 | `komawari remove NAME` deletes one comic from the Vita and asks before doing it. | Frees space on the card; the prepared copy on the computer stays. |
| 2026-10-10 | `komawari install` copies the reader's package to `ux0:data/komawari.vpk`. Installing it is still done in VitaShell. | Owner's name for the command. A computer cannot install a package on the Vita over USB. |
| 2026-10-10 | No transfer over Wi-Fi. | Owner's choice. |
| 2026-10-10 | The detector-comparison commands (`sample`, `add`, `detect`, `report`), the Magi runner and its dependencies (PyTorch, transformers and six more) are removed. | Kumiko is chosen and `komawari test` covers checking it. The command list is shorter and the environment went from 69 packages to 12. |
| 2026-10-10 | The reading direction is not guessed from the pictures. `prepare` and `test` take it from `--ltr` or `--rtl`, else from the archive's `ComicInfo.xml`, else they assume right to left, and they print which of the three it was. | It cannot be read reliably from the pictures. `ComicInfo.xml` is the one place an archive can state it. Many archives hold only pictures, so right to left stays the fallback. |
| 2026-10-10 | From `ComicInfo.xml` only the `Manga` field is read: `YesAndRightToLeft` means right to left, `No` means left to right, `Yes`, `Unknown` or a missing field mean no answer. | Those are the four values in the ComicInfo 2.0 schema; `Yes` marks a manga without stating its direction. |
| 2026-10-10 | Deleted: the 22 test pages (`pages/`), the comparison reports (`results/`) and the downloaded Magi model (1.6 GB). | Owner's request; nothing uses them. The findings stay in `docs/notes.md`. The `.gitignore` lines for the two folders went with them; the rule that ignores every image and archive stays. |
| 2026-10-10 | The manual is one HTML page, `index.html` in the top folder, built by `komawari manual` from `README.md` followed by `docs/install-on-vita.md`. | Owner's request: a page that explains how to use the project and its options, built from the Markdown text. Using the two existing files means nothing is written twice. |
| 2026-10-10 | `README.md` is the user's guide, and the commands and options in it are written by hand, not taken from the command-line code. | The owner asked for a page built from the Markdown description. The price is that `README.md` has to be changed together with `cli.py`. |
| 2026-10-10 | `index.html` is committed, although it is generated. | It is there to be opened straight after a clone, and it holds no comic material. The price is that it must be rebuilt and committed whenever its two source files change. |
| 2026-10-10 | Markdown is turned into HTML with the `markdown-it-py` library. | It ships type information, so `pyright` strict passes without extras; it brings one small dependency (`mdurl`); and it hands over its list of tokens, which is what giving headings link names and redirecting links needs. Python-Markdown needs a separate stubs package; writing a converter of our own would be more code to get wrong. |
| 2026-10-10 | The manual takes its mark, colours and name font from `artwork.py` and `reader/artwork/`. | One look for the reader and its manual, defined in one place. |
| 2026-10-10 | The user's guide (`README.md`) is short and written for someone who wants Komawari on their Vita and is not technical: numbered steps, commands to paste, no account of how it works. | Owner's request: the first version was too long and too chatty. |
| 2026-10-10 | The manual page is built from `README.md` alone. `docs/install-on-vita.md` is folded into it and removed; what the guide leaves out (the folders on the Vita, copying over Wi-Fi) is in `docs/notes.md`. | One short set of instructions instead of two that overlap, and one place for the buttons. This replaces the decision above to build the page from two files. |
| 2026-10-10 | The guide leaves out what only a developer needs: `komawari artwork`, `komawari manual`, the reader in a window on the computer, the emulator, the list of folders. | They are in `CLAUDE.md` and `docs/notes.md`, and `--help` lists every command. |
| 2026-10-10 | The guide installs the Vita SDK into `~/vitasdk` and gives `VITASDK` on the same line as the one command that needs it. | The build finds the SDK there by itself, so the reader does not have to edit their shell's settings. Checked: `vdpm` runs that way from an empty environment. |
| 2026-10-10 | The page's header and browser title say "Built for the PS Vita" next to the tagline. | Owner's request. |
| 2026-10-10 | Komawari is public on GitHub as `kwap/komawari`, under the MIT licence. | Owner's choice of a public project with a permissive licence. MIT is the shortest of those, and it is what cJSON and much Vita homebrew use. Kumiko, which is AGPL, is not copied into the repository or into a release: it is a submodule and runs as a separate program. |
| 2026-10-10 | Nothing in the repository names a specific comic or describes anyone's own computer. The public history starts with one commit. | Owner's request. The earlier commits held working notes that did both. |
| 2026-10-10 | GitHub builds `komawari.vpk` on every push (`.github/workflows/build.yml`), and a pushed tag that starts with `v` publishes it as a release. | Owner's request. A broken build is noticed at once, and nobody has to install the Vita SDK just to read comics. |
| 2026-10-10 | `komawari install` downloads the reader from the latest release when it was not built on this computer. The download is done by `curl`. | One command for the user, whichever way the reader came about. `curl` is already on macOS and Linux and finds the system's certificates by itself, so there is no new dependency. |
| 2026-10-10 | The user's guide installs only `uv` (on Linux also `git` and `bsdtar`). Building the reader is described in `docs/notes.md`. | With a release to download, a reader of the guide never builds anything. This replaces the decision above to install the Vita SDK in the guide. |
| 2026-10-10 | The manual is also the website: GitHub Pages serves `index.html` from the top folder of `main`. | The page is already built and committed, so the website needs no build of its own. |
| 2026-10-10 | The website's address is https://kwap.io/komawari/. | Owner's request: every project's page under the one domain. The domain is set on the account's personal site project, so GitHub serves each project's page under it; the old `kwap.github.io` address is sent on. |
| 2026-10-10 | The manual looks like the owner's home page, kwap.io: heavy narrow capitals, thick rules, and a switch between light and dark. It no longer uses the lettering of the reader's artwork. | Owner's request: the pages of their projects should look like one family. |
| 2026-10-10 | The manual's two fonts are files in `fonts/`. They are not loaded from kwap.io or from a font service. | The page also works when opened from a clone or without a network, and it depends on no other project. |
| 2026-10-11 | Blocks of commands in the manual use the colours of the Tokyo Night theme, light or dark with the page, and each has a copy button. A script in the page adds both. | Owner's request: the plain blocks looked flat, and copying is a convenience for readers. Doing it in the page keeps `README.md` plain Markdown; without the script the blocks are still readable. |
